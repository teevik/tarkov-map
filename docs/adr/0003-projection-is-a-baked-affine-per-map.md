# Projection is one pre-baked game→image affine per Map, decided by fetch_maps

Upstream tarkov.dev places markers through Leaflet: rotate `(x, z)` by `coordinateRotation`, then either a `Transformation` onto a tile pyramid or a stretch of the SVG onto the box `svgBounds ?? bounds` (see `docs/research/tarkov-dev-coordinate-oracle.md`, branch `research/coordinate-oracle`). The current port mirrors those raw fields and picks the path with `rotation == 270`, which is wrong for Reserve (needs `svgBounds`) and Icebreaker (tiles at 180°). We decided that the domain `Map` carries a single **Projection**: `game_to_image: Transform2D<f64, Game, Image>` (euclid) plus `image_size: Size2D<f64, Image>` — non-optional, no rotation, transform array or tiles/SVG flag — and that `fetch_maps`, as the anti-corruption layer that already knows which image it bundled, bakes that affine: tiles → rotation ∘ upstream transform ÷ tile size; SVG → rotation ∘ box-normalisation over `svgBounds ?? bounds` ∘ the `xMidYMid meet` letterbox offset, so the bundled PNG keeps the SVG's own aspect and markers land pixel-for-pixel where upstream puts them. Core has one code path (`Map::project(GamePos) -> ImagePos`), and the 38 golden vectors from the oracle research test the baking (in `fetch_maps`) and the bundled `maps.ron` (a catalogue-level test in adapters, beside the `maps.ron` loader, since `ron` stays out of core; the vectors themselves live as one data file, `crates/core/testdata/projection-oracle.ron`, shared by both).

## Consequences

- **Bounds are not the image box.** `Map.bounds: Box2D<f64, Game>` is the playable extent used by Map Suggestion's inside-test and to describe the map in metres; the SVG box (`svgBounds`) never reaches the domain. `logical_size` is gone: the image is drawn at its own pixel aspect (today's drawing stretched the square tile maps to the bounds aspect) and "consistent zoom across maps" is a derived `metres_per_pixel()` on the Projection.
- **Icebreaker's bounds are derived, not copied.** Upstream's Icebreaker `bounds` are a copy of Factory's, which would make every Factory fix ambiguous between two Maps and silence Map Suggestion. Rule in `fetch_maps`: for tile-placed maps, bounds are the tile image's rectangle unprojected through the affine; for SVG maps, upstream's `bounds` are kept.
- **Heading needs no rotation field.** The on-image heading is the game-space heading vector `(sin yaw, cos yaw)` pushed through the affine's linear part (`transform_vector`) and normalised — yaw 0 points down on 180° maps and left on Factory (90°), matching upstream's `yaw + coordinateRotation (+180)` rule. Icebreaker's non-uniform scale shears the arrow exactly as it shears the image.
- **Schema.** `maps.ron` is domain-shaped: `Serialize`/`Deserialize` derived on the domain types (core enables euclid's `serde` feature; positions serialise as `(x, y)` tuples), no DTO layer, no schema version — the file is regenerated with every release by the same repository. Parsing (`ron`) happens outside core; core validates the loaded `MapCatalog` (non-empty, unique `MapId`s, positive image sizes, invertible affines) and failure is fatal (ADR-0001).
- The affine field is not human-readable in `maps.ron`; the raw upstream fields live only in `fetch_maps`'s fetch types and the research note.

## Considered options

- Mirror upstream's fields (`rotation`, `transform`, `bounds`, `svgBounds`, tiles/SVG flag) and choose the path in core — rejected: core would carry Leaflet's two placement models and a branch that only `fetch_maps` can justify; the enum would exist for one map (Reserve) and one predicate.
- Ignore letterboxing (≤ 0.5 % error) — viable, but free to do right once the affine is baked.
- A hand-maintained bounds override table for Icebreaker — rejected in favour of deriving from the tile rectangle; nothing to rot.
